1스타일 핵심

환경

  • Sass(SCSS) 모듈 시스템: @use / @forward 사용. 예전 방식인 @import는 쓰지 않음
  • 빌드 도구 없이 에디터에서 컴파일 (package.json에 sass가 없고 .css.map이 함께 커밋됨 → Live Sass Compiler류로 추정)
  • 폰트: Pretendard Variable(woff2) 직접 호스팅 + preload. Pretendard GOV는 대체용으로 준비

아키텍처

  • 공통 번들과 페이지별 CSS 이원화: 무거운 페이지 스타일은 그 페이지에서만 로드 (예: mypage.html → mypage.css만 추가)
  • 문서화 헤더 규칙: "style.css 직접 수정 금지", "디자이너 외 수정 시 문의" 등

2HTML / 마크업

  • 진행 방식: 정적 HTML 퍼블리싱 → 개발자가 같은 파일을 EJS 템플릿으로 전환 (서버 사이드 렌더링)
    • 초기: dataincludes 속성 + fetch로 header/footer를 클라이언트에서 include (design.js)
    • 이후: <%- include('partials/header.html', { pageTitle, leftIcon }) %> — 파셜에 파라미터를 넘기는 구조
  • partials: header(타이틀·좌우 아이콘 파라미터 + 로딩 화면), footer(하단 탭바), favicon, modal 2종
  • 시맨틱·접근성: header / main / section / footer / nav, lang="ko", 버튼 aria-label, type="button" 명시, 이미지 alt
  • 모바일 대응: viewport-fit=cover(노치), min-height: 100dvh, word-break: keep-all(한글 줄바꿈), -webkit-tap-highlight-color: transparent
  • 네이밍: page--mypage, visual__text-wrap, field-info--selected 등 BEM 비슷한 규칙

3프론트엔드 JS 2순위

  • 캐시 무효화: 모든 정적 리소스에 ?v=<버전>

5인터뷰 대비: 물어볼 만한 약점과 답변 방향

1. 같은 코드 중복

마키 로직이 JS 9개 파일에 복붙, <style> 인라인 블록도 index·mypage 중복.
→ "공통 모듈화가 다음 과제였다" + 본인이 중복을 줄인 사례(라벨 공통화)를 함께 말하면 강점.

2. !important 남용

유틸리티·상태 라벨에 사용.
→ "공통 라벨 색상이 페이지 스타일보다 우선해야 해서 의도적으로 썼다."

3. 상태 → 클래스 매핑 불일치

index.html에서 '준공완료' → 'progress', '수행중' → 'completed'로 이름과 의미가 어긋남.
→ 질문받으면 인지하고 있다고 답할 것.

4. 빌드 파이프라인 부재

에디터에서 컴파일하고 산출 CSS를 커밋.
→ 개선안으로 sass CLI / Vite 도입 제시.

6경력기술서 문장 예시

  • SCSS 모듈 시스템(@use/@forward)으로 디자인 토큰을 Sass map으로 정의하고 CSS 변수를 자동 생성하는 스타일 아키텍처를 운영했습니다.
  • clamp() 기반 유동 타이포그래피 믹스인으로 모바일·태블릿(iPad 820px 포함) 반응형을 구현했습니다.
  • 페이지마다 흩어진 현장 상태 라벨과 빈 상태 UI를 공통 컴포넌트로 통합해 화면 간 일관성을 높였습니다.
  • 정적 퍼블리싱 결과물을 EJS 파셜 구조로 전환하는 과정에서 개발자와 협업했습니다(헤더·로딩·모달 파셜화).
